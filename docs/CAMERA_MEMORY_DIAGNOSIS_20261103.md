# JETANK 메모리 증가 현장 진단 — 2026-11-03

## 직접 관측

Jupyter 커널에서 `free -m`, 프로세스 RSS, cgroup 메모리, 카메라 클래스와 스레드를 조회했다. 카메라 초기화나 중지, 커널 재시작은 수행하지 않았다. 조회 도중 카메라 객체와 영상 서버가 존재하는 것을 확인했다.

- 시스템 RAM: 3964MiB.
- 연속 30초 관측 used: 1105 → 1105 → 1104 → 1105MiB.
- available: 약 2678MiB. buff/cache: 약 868~869MiB.
- Jupyter 서버 PID 6 RSS: 531012KiB(약 519MiB), 관측 중 일정.
- 커널 PID 88 RSS: 249256KiB(약 243MiB), 30초 관측 중 일정.
- cgroup 사용량: 약 1.04GiB, 캐시 약 425MiB와 익명 RSS 약 622MiB 포함.
- cgroup memory.failcnt: 0. 조회한 dmesg에서 OOM 기록 없음. 과거 OOM이 없었다고 보장하지는 않음.
- 카메라 300×300, 프레임 변경 확인, cap open, 캡처 스레드 생존.
- 영상 클라이언트 핸들러 3개가 동시에 실행 중.
- 현재 컨테이너 프로세스 목록에 Depth 추론 프로세스 없음. Depth Pro는 PC에서 실행.

## 해석

이번 관측에서는 지속적인 메모리 증가를 재현하지 못했다. 사용자가 본 0.4GB 이후의 증가를 곧바로 누수라고 단정할 수 없다. Jupyter 커널, 카메라/GStreamer, 연결 처리 초기화 및 캐시 증가가 가능한 설명이나, 초기 0.4GB 시점의 항목별 측정값은 없다. 이전 4GB 근접 현상의 원인도 현재 자료만으로 확정할 수 없다.

Jupyter는 컨테이너 안에 있어 ps에는 호스트의 카메라 서비스 등 모든 프로세스가 보이지 않는다. 호스트 측 증가가 발생하면 이 목록만으로 원인을 특정할 수 없다.

## 실제 설치 코드에서 확인한 위험 요소

1. `jetbot.camera.opencv_gst_camera.OpenCvGstCamera._gst_str()`의 마지막이 `appsink`다. `max-buffers=1 drop=true sync=false` 같은 제한이 없어 소비 지연 시 버퍼가 누적될 수 있다. 현재 누적이 발생했다는 증거는 없다.
2. `OpenCvGstCamera.instance()`는 이름과 달리 매번 `OpenCvGstCamera(*args, **kwargs)`를 생성한다. 초기화 셀 반복 실행 시 기존 객체를 stop하지 않으면 캡처 자원이 중복될 수 있다. 현재 관측한 캡처 스레드는 하나다.
3. `traitlets.dlink`가 카메라 프레임을 Jupyter 이미지 위젯에 전달하는 코드다. 수신 지연 시 위젯 통신 경로도 진단 대상이다. 현재 메시지 적체는 직접 측정하지 않았다.
4. MJPEG 핸들러가 클라이언트마다 JPEG 인코딩한다. 관측한 3개 연결은 부하를 늘리지만, 연결 3개 자체를 메모리 누수 증거로 볼 수 없다.

## 후속 진단 기준

증가 시 시스템 used/available, PID별 RSS, cgroup rss/cache를 같은 시각에 비교한다. 커널 RSS가 늘면 캡처/위젯/인코딩 경로, Jupyter 서버 RSS가 늘면 메시지 전달/연결 버퍼, 컨테이너 RSS가 일정한데 전체 used가 늘면 호스트 프로세스·공유 GPU/드라이버 메모리를 조사한다. 캐시 증가와 available 감소가 동반되는지도 구분한다.

카메라 안정화 시 권장 변경은 단일 캡처 객체 재사용, appsink 큐 제한, 위젯 미리보기 통신 분리, JPEG 1회 생성 후 공유다. 이번 요청에서는 원인 조사만 수행했으며 실행 중 카메라 코드는 변경하지 않았다.
