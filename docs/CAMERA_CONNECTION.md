# JETANK 카메라 영상 연결

## 현재 상태

2026-11-03 사용자 Jupyter 로그인 후 `JETANK/Test_camera/Test_Camera.ipynb`에서 실제 서버 코드와 주소 `http://70.12.231.81:8765/video`를 확인했습니다. 현재 커널에는 카메라 객체가 없어 기존 카메라 초기화 셀과 영상 서버 셀만 실행했습니다. 서버의 인증 없는 LAN 공개 범위는 자동 승인 검토에서 처음 거부되어 실행을 보류했고, 사용자가 로컬 시연 동안의 실행을 명시적으로 승인한 뒤 실행했습니다. 모터·서보 셀은 실행하지 않았습니다.

데스크톱 `/video` 화면에서 실제 JPEG 디코딩과 300×300 영상 표시, 프레임 번호 증가(208→248)를 확인했습니다. 형식은 MJPEG입니다. 확인된 설정으로 실행하는 스크립트는 `scripts/start-video.ps1`입니다. 영상 서버는 Jupyter 커널 종료나 서버 중지 후 다시 실행해야 합니다.

## 기존 Jupyter 카메라 연결용 브리지

제조사 JETANK 노트북은 `jetbot.Camera`와 `bgr8_to_jpeg`로 ipywidgets 영상을 표시하는 예제를 제공합니다. 현재 장치의 기존 노트북에서도 같은 카메라 초기화 방식과 별도 MJPEG 서버 코드를 확인했습니다.

- 제조사 문서: https://www.waveshare.com/wiki/JETANK_Control
- 제조사 예제: https://github.com/waveshare/JETANK/blob/main/JETANK_2_ctrl/JETANK_2_ctrl_en.ipynb

`robot/JETANK_camera_bridge.ipynb` 또는 `robot/jetank_camera_bridge_cell.py`에 카메라 전용 브리지 셀을 준비했습니다. 기존 영상이 실제로 실행 중인 노트북의 **같은 커널**에서 실행합니다. 별도 커널에서는 기존 카메라 객체를 공유할 수 없으므로 카메라를 중복 초기화하지 않고 기존 노트북에 셀을 붙여 넣습니다.

이 셀은 기존 `camera.value`와 `bgr8_to_jpeg`를 재사용합니다. 모터·서보·카메라 생성이나 기존 카메라 종료를 수행하지 않습니다. 원본 카메라는 매 프레임 새 배열을 게시하는 JetBot traitlets 방식을 기대합니다. 배열 객체가 갱신되지 않으면 브리지는 새 프레임으로 취급하지 않으며 3초 후 스냅샷 요청에 503을 반환합니다. 인플레이스 배열 갱신 방식의 카메라는 별도 관측 이벤트 어댑터가 필요합니다. 수신 시각은 촬영 시각을 대신하지 않습니다.

브리지는 OS가 선택한 빈 포트에서 JPEG 스냅샷을 제공하고 정확한 URL을 출력합니다. 이것은 새로 생성하는 영상 서비스이며 기존 포트를 추측하는 방식이 아닙니다. 기본 바인딩은 `0.0.0.0`이고 인증이 없으므로 신뢰하는 로컬 네트워크에서 사용하고, 사용 종료 시 `rove_camera_bridge.stop()`을 실행합니다. Python 3.6+ 표준 라이브러리를 사용하며 기존 JPEG 인코더 외의 로봇 측 패키지 설치는 없습니다.

출력된 정확한 URL을 데스크톱의 `JETANK_CAMERA_URL`로, 형식을 `snapshot`으로 설정하고 데스크톱 서버를 재시작하면 기존 `/video` 화면으로 연결할 수 있습니다. 브리지 셀은 현재 로컬 파일로 준비된 상태이며 아직 장치에 업로드하거나 실행하지 않았습니다.

## 실행

현재 영상 프로그램에서 사용하는 **전체 영상 URL**을 확인합니다. IP만으로는 URL을 완성할 수 없습니다. 브라우저 주소가 웹페이지인 경우 페이지에 포함된 실제 `<img src>` 또는 영상 서버 코드를 확인해야 합니다. 기존 Jupyter/JetBot 위젯, RTSP 또는 WebRTC 영상은 현재 HTTP JPEG 수신기에 바로 연결되지 않을 수 있습니다.

확인한 정보로 PowerShell 환경변수를 설정합니다. 아래의 대괄호 문자열은 실제 확인값으로 교체하며 그대로 실행하지 않습니다.

```powershell
$env:JETANK_MODE = 'mock'
$env:JETANK_CAMERA_URL = '<확인한 전체 HTTP 또는 HTTPS 영상 URL>'
$env:JETANK_CAMERA_FORMAT = 'mjpeg'
.\.venv\Scripts\python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

http://127.0.0.1:8000/video 에 접속해 ‘영상 연결’을 누릅니다. 환경변수는 서버 시작 때 읽으므로 변경 후 서버 재시작이 필요합니다. `.env.example`은 참고 설정이며 `.env` 자동 로딩은 하지 않습니다.

## 지원 형식

| 설정 | 실제 URL 응답 |
|---|---|
| `mjpeg` | `multipart/x-mixed-replace; boundary=...`의 JPEG 프레임 |
| `snapshot` | `image/jpeg` 스냅샷. 성공 후 약 0.2초 간격으로 다시 요청 |

RTSP/HLS/WebRTC, MP4, PNG, HTML 페이지, 인증이 필요한 영상 및 리다이렉트는 현재 지원하지 않습니다. 로그인·인증정보가 포함된 URL은 거부합니다. 실제 서버가 다른 방식이라면 해당 서버 코드와 전송 방식을 확인한 뒤 어댑터를 추가합니다.

## 화면과 연결 동작

- 영상 연결, 종료, 전체 화면
- 설정 여부, 연결 상태, 프레임 번호, 해상도, 마지막 수신 시각
- 서버가 수신한 프레임을 브라우저에서 JPEG로 디코딩한 뒤 표시
- 마지막 수신 프레임이 5초 이상 오래되면 표시 중단
- 오류 시 1→2→4→8→10초 간격으로 재시도
- 서버가 최신 한 프레임만 유지하며, 브라우저는 약 0.25초 간격으로 확인하므로 원본 FPS를 그대로 재생하지 않습니다. 지연·처리량은 실제 장비로 측정해야 합니다.
- 연결은 서버 전체에서 공유됩니다. 한 사용자의 종료가 다른 사용자 화면에도 반영됩니다. 탭을 닫아도 서버 수신은 계속되므로 종료 버튼 또는 서버 종료로 중단합니다.
- 영상 수신은 모터 제어와 독립적입니다. 카메라가 연결되어도 실제 로봇 제어가 연결되었다고 표시하지 않습니다.

서버는 환경변수에 명시한 주소만 요청하며, 브라우저에서 임의 URL을 전달하는 프록시 API는 제공하지 않습니다. 요청 타임아웃 5초, JPEG 프레임 최대 5 MB, multipart 헤더 최대 16 KB를 적용합니다. 외부 공개를 전제로 한 인증은 없으므로 기존 로컬 개발 서버 범위에서 사용합니다.

## API

- `GET /api/camera/status`: 설정 여부, 수신 상태. 원본 URL은 노출하지 않음
- `POST /api/camera/connect`: 설정된 영상 수신 시작. 미설정이면 409
- `POST /api/camera/disconnect`: 공용 수신 종료 및 프레임 삭제
- `GET /api/camera/frame`: 최신 JPEG, no-store. 최신 프레임 없으면 503

## 검증

전체 37개 테스트 통과. 카메라 테스트는 Mock HTTP 응답으로 연결 종료, 청크 분할, multipart Content-Length 유무, JPEG 내부 썸네일 마커, 잘못된 응답, 리다이렉트 거부, 오래된 프레임, 크기 제한과 API 응답을 확인합니다. 이 결과는 실제 JETANK 연결 성공을 뜻하지 않습니다.

다음에 필요한 정보는 영상 전체 URL 또는 JETANK에서 실행 중인 카메라 서버 코드입니다. 포트·경로가 아직 없다면 먼저 기존 영상을 보는 프로그램 이름과 실행 방법을 확인합니다.


## 확인된 설정으로 바로 실행

```powershell
.\scripts\start-video.ps1
```

브라우저에서 http://127.0.0.1:8000/video 를 열고 ‘영상 연결’을 누릅니다. 현재 시연용 서버는 영상 수신 중인 상태로 유지했습니다. 데스크톱의 ‘연결 종료’는 수신만 중단하고 JETANK 서버 자체를 종료하지 않습니다. 로컬 시연 종료 시 기존 노트북의 `server.shutdown(); server.server_close()` 셀로 영상 서버를 종료할 수 있습니다. 커널 전체 실행이나 모터 제어 셀 실행은 필요하지 않습니다.

모듈 검증은 브리지 테스트를 포함해 39개 통과했습니다. 별도로 실제 MJPEG 수신과 브라우저 표시도 확인했습니다. 준비한 대체 브리지는 현재 시연에 사용하지 않았습니다.
